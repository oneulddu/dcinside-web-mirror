# 성능·버그 개선 계획과 결과

기준 커밋은 `522a52e`다. 사용자 요청에 따라 Opus 5.5가 수집기, 서비스·캐시,
라우트, 미디어, 브라우저 스크립트를 읽고 개선 계획을 작성했다. 주 에이전트가
아래 다섯 항목을 재현하고 구현했다. 화면 디자인, 요청 차단 회피 정책,
의존성 버전 범위와 배포 설정은 이번 변경 대상이 아니다.

| 항목 | 확인된 문제 | 적용 결과 |
| --- | --- | --- |
| 목록 오류 구분 | 원본 조회 실패가 정상 빈 목록처럼 반환되고 새로고침이 정상 캐시를 덮음 | 수집 실패를 별도 예외로 전달. 유효한 기존 캐시가 있으면 복사본을 반환하고 TTL은 유지. 없으면 503·`Retry-After: 3`·`no-store` |
| 관련 글 일부 결과 | 뒤 페이지 실패·지연이 앞서 찾은 관련 글까지 버림 | 남은 조회 시간 안에서 뒤 페이지를 시도하고, 실패·시간 초과 시 확보한 행과 `has_more: null` 반환. 마지막 성공 행에서 재시도 가능 |
| 동시 조회 오류 | 게시판 대기 요청에 게시글 오류 타입을 전달하여 페이지 탐색 복구를 건너뜀 | 게시판 계열 대기 요청에 `BoardUnavailableError` 전달 |
| 첫 페이지 재사용 | 최신 글 번호 추정과 대상 글 탐색이 서로 다른 크기로 같은 페이지를 요청 | 전체 페이지 캐시를 공유하여 중복 요청 제거 |
| 전체 조회 시간 | 개별 네트워크 제한만 있어 URL 폴백과 잠금 대기가 누적됨 | 목록·정확한 작성 시간 조회와 동시 조회 대기에 기본 25초 제한 적용 |

## 유지하는 동작과 완료 조건

- 실제 빈 게시판·검색 결과는 정상 응답으로 유지한다. 관련 글의 엄격한 마지막
  페이지 판정은 기존 `raise_on_failure`로 유지하고, 목록에는 원본 수집 실패만
  구분하는 `raise_on_unavailable`을 사용한다.
- 실패가 끝까지 확인되지 않은 초기 관련 목록을 기존 스냅샷 위에 저장하지 않도록,
  관련 글 엔드포인트는 `has_more`가 확정된 경우에만 초기 스냅샷을 갱신한다.
  본문에 포함된 관련 글 저장은 기존대로다. 부분 결과를 전체 목록의 끝으로 취급하지 않는다.
- 만료된 목록은 오류 복구 과정에서 되살리지 않는다. 원본 작업이 취소·실패하면
  진행 중 조회 등록을 제거하고 다음 요청에서 다시 시도할 수 있다.
- 대기 요청의 취소·시간 초과는 공유 원본 작업을 취소하지 않는다. 원본 작업 자체가
  제한 시간을 넘으면 취소하고 오류를 대기 요청에 전달한다.
- `MIRROR_BOARD_FETCH_TIMEOUT`은 기본 25초, 최소 1초다. 목록 오류는 503이며,
  `/board/times`는 기존 오류 계약인 502 JSON을 유지한다. 관련 글의 기존 12초 제한은 유지한다.

## 검증

Python 3.12.13 임시 가상환경에서 저장소의 `requirements-dev.txt`를 설치했다.
기존 `.venv`는 Python 3.9이므로 변경하지 않았다.

- 기준 전체 테스트 683개, JavaScript 상태 전이 테스트 3개 통과.
- 수정 전에 정상 캐시 유실, 빈 목록 200 응답, 뒤 페이지 실패, 잘못된 공유 오류 타입,
  중복 원본 요청, 전체 시간 제한 누락을 회귀 테스트로 재현했다.
- 수정 후 관련 검사 295개, 전체 `make test` 698개 통과. 전체 검사에는 기존 JavaScript
  상태 전이 검사도 포함된다.
- 독립 코드 리뷰가 찾은 뒤 페이지 시간 초과 누락을 추가 재현·수정했다. 앞 페이지
  30ms·뒤 페이지 1초·전체 예산 100ms 조건에서 부분 결과 보존을 확인하고,
  외부 요청 취소는 계속 전파되는지 검사했다. 수정 후 관련 검사 157개가 통과했고,
  같은 리뷰어가 지적 해결을 확인했다. 추가 지적은 없다.
- 최신 글이 첫 페이지에 있고 페이지 캐시가 비어 있는 모형 API에서 첫 페이지 호출이
  **2회 → 1회**로 감소했다. `test_latest_id_estimate_reuses_first_page_for_cursor_lookup`으로 재현한다.
- 느린 원본 200ms와 전체 제한 10ms를 사용하여 실제 수집 취소, 오류 응답,
  8개 동시 요청의 오류 전달·등록 정리·다음 요청 복구를 확인했다.

```bash
make test PYTHON=/path/to/python3.12-venv/bin/python
node --test tests/javascript/*.test.cjs
```

운영 트래픽·외부 원본 응답 시간은 측정하지 않았다. 요청 횟수 감소는 위 모형 조건의
결과이며 운영 응답 속도 보장값이 아니다. 별도 데이터 마이그레이션은 없으며,
문제가 생기면 변경 커밋을 되돌리고 기존 절차로 재배포할 수 있다.

## 후속 조사 후보

Opus가 다음 항목은 근거 또는 측정이 더 필요하다고 분리했다. 원본 요청의 host별
직렬화 완화는 429 발생 시 추가 요청을 억제하는 기존 계약에 영향을 주므로 유지했다.
댓글 0개일 때 PC 폴백이 불필요한지는 실제 응답·운영 로그로 확인해야 한다.
큰 본문의 HTML 가공 캐시, 목록·관련 페이지 캐시 통합, 정적 자산 압축 최적화는
각 처리 비용을 측정한 후 판단한다. 기존 동시 요청 병합과 과거 감사에서 해결한
문제는 이번 성능 개선으로 다시 집계하지 않았다.
